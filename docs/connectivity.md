# 连接方案：客户端与服务端均无公网 IP

> 场景：服务端跑在自己的电脑（宿舍/家里的 PC 或闲置笔记本），客户端是 Windows/Android 手机。
> 双方都躲在 NAT 后面，没有公网 IP，互联网上无法直接互访。以下按推荐顺序给出方案。

## 方案对比

| 方案 | 原理 | 成本 | 难度 | 稳定性 | 适用 |
|---|---|---|---|---|---|
| ① Tailscale / ZeroTier | WireGuard 虚拟组网 + NAT 打洞，打不通走官方中继 | 免费（个人） | ★ 极低 | 高 | **首选** |
| ② Cloudflare Tunnel | 服务端 cloudflared 出站连接 CF，客户端走 CF 域名访问 | 免费（需域名） | ★★ 低 | 高 | 只需 HTTP API |
| ③ frp 自建中继 | 买一台有公网 IP 的 VPS 做流量中转 | ~¥10-30/月 | ★★ 中 | 高 | 已有 VPS |
| ④ 自研 P2P 打洞 | STUN 打洞 + TURN 中继（QUIC/WebRTC） | 0 | ★★★★ 很高 | 看运气 | 不推荐自建 |

## ① Tailscale（推荐）

- 服务端和每个客户端都装 Tailscale，登同一账号，各自拿到一个 `100.x.x.x` 虚拟 IP。
- 同一局域网内自动走本地直连（速度不受影响）；跨网时先尝试 P2P 打洞，
  打不通自动经 Tailscale 官方 DERP 中继（免费但国内速度一般）。
- 客户端里服务端地址直接填 `http://100.x.y.z:8787`，代码零改动。
- 进阶：用开源的 **Headscale** 自建控制面，中继节点也可以自建（derper），
  完全不依赖第三方账号。
- Android 端有官方 App，Windows 端装官方客户端即可。

## ② Cloudflare Tunnel

- 服务端跑 `cloudflared`（出站连接，无需开端口），把 `localhost:8787` 映射到
  `https://api.你的域名.com`；客户端直接填这个 HTTPS 地址。
- 优点：客户端在任何网络都能访问、自带 HTTPS；缺点：需要托管在 CF 的域名，
  国内访问 CF 速度不稳定。

## ③ frp 中继（有 VPS 时）

- VPS 跑 `frps`，服务端跑 `frpc` 把 8787 端口映射出去；客户端访问 `VPS_IP:port`。
- 适合已经有一台云服务器的同学；没有的话为这一个用途买 VPS 不划算。

## ④ 自研打洞（评估结论：不值得）

- 需要 STUN 探测 NAT 类型 + UDP 打洞 + 打洞失败时的 TURN 中继 + 心跳保活，
  工作量相当于再造一个 Tailscale 子集；且校园网/家庭宽带的 NAT 类型不可控，
  对称型 NAT 必然要回落中继。作为个人项目 ROI 太低，**结论：直接用方案 ①**。

## 本项目的落地建议

1. 校内使用：客户端与服务端同在校园网，直接填局域网 IP（如 `http://10.x.x.x:8787`）。
2. 校外使用：服务端装 Tailscale，客户端（手机流量）也装，填 `100.x.x.x` 地址。
3. 若以后有 VPS / 域名，再叠加方案 ②或③ 做备份入口。
4. 服务端 API 已内置 Bearer Token 认证，公网可达时也建议改强 `auth.password`
   并考虑加 HTTPS（如 Caddy 反代）。
